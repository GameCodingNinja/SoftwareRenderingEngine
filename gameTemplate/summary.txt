Native Linux Window & Framebuffer - Project Summary
=====================================================

WHAT WE'RE DOING
-----------------
Right now, the software rendering engine uses SDL (a third-party library) to
create the game window and the pixel buffer we draw to. We're replacing that
with native Linux code so the engine talks directly to the display server.

On modern Linux there are two display servers:
  - Wayland (the new default on most distros, including Arch)
  - X11 (the legacy system, still widely used)

We'll support both by trying Wayland first and falling back to X11 if
Wayland isn't available.

WHY WE'RE DOING IT
-------------------
  - Removes the SDL dependency for window/rendering (SDL stays for audio,
    gamepad, and timer)
  - Gives us direct control over the framebuffer and window behavior
  - Better performance potential (no SDL middle-man for pixel blitting)
  - Educational: understand how display servers actually work under the hood

HOW IT WORKS
-------------
We create new classes in the library/system folder, separated by concern:

  WINDOW CLASSES (creating/managing the OS window):

  1. IWindow (interface)
     - Defines the contract for window operations: Create, Show, SetTitle,
       SetFullScreen, PollEvents, GetFrameBuffer, etc.
     - This is the only class the rest of the engine talks to for window
       management.

  2. CWaylandWindow (implements IWindow)
     - Uses the Wayland protocol (wl_display, wl_compositor, xdg_wm_base)
       to create and manage a native Wayland window.
     - Creates and owns a CWaylandFrameBuffer internally.

  3. CX11Window (implements IWindow)
     - Uses Xlib (XOpenDisplay, XCreateWindow) to create and manage a
       native X11 window.
     - Creates and owns a CX11FrameBuffer internally.

  FRAMEBUFFER CLASSES (pixel buffer you draw to):

  4. IFrameBuffer (interface)
     - Defines the contract for framebuffer operations: GetPixels,
       GetWidth, GetHeight, Clear, Flip.
     - The software renderer only needs this to do its work.

  5. CWaylandFrameBuffer (implements IFrameBuffer)
     - Uses wl_shm + shared memory for the pixel buffer.
     - Flip attaches and commits the buffer to the Wayland surface.

  6. CX11FrameBuffer (implements IFrameBuffer)
     - Uses XImage (or XShmImage) for the pixel buffer.
     - Flip calls XPutImage to display the buffer.

  FACTORY:

  7. CreateNativeWindow() factory function
     - Tries Wayland first (wl_display_connect). If it succeeds, creates
       a CWaylandWindow (which creates its CWaylandFrameBuffer).
     - If Wayland fails, tries X11 (XOpenDisplay). If it succeeds, creates
       a CX11Window (which creates its CX11FrameBuffer).
     - Returns a unique_ptr<IWindow> so the engine doesn't know which
       backend is active.

  In the future, a CWindowsWindow + CWindowsFrameBuffer could be added
  behind the same interfaces for Windows support.

THE PLAN (5 PHASES)
--------------------
  Phase 1: Define the interfaces and data structures
           - Create IWindow and IFrameBuffer interfaces
           - Create a simple surface data struct to replace SDL_Surface
           - No functional changes yet, just the contracts

  Phase 2: Build the X11 backend
           - Create CX11Window (Xlib window management, events)
           - Create CX11FrameBuffer (XImage pixel buffer, XPutImage flip)

  Phase 3: Build the Wayland backend
           - Create CWaylandWindow (Wayland protocol, xdg-shell, events)
           - Create CWaylandFrameBuffer (wl_shm pixel buffer, surface commit)

  Phase 4: Wire it all together
           - Create factory that tries Wayland first, falls back to X11
           - Update the engine (CDevice, CBaseGame, CSoftwareRender, etc.)
             to use IWindow/IFrameBuffer instead of SDL window/surface

  Phase 5: Test and polish
           - Run automated and manual tests on both backends
           - Fix issues, clean up, verify no regressions

  Each phase stops for user review before proceeding to the next.

WHAT CHANGES IN THE EXISTING CODE
-----------------------------------
  - CSoftwareRender stops using SDL_Surface. Instead it gets pixel buffer
    pointer, width, and height from IFrameBuffer.
  - CRender2d (the per-triangle render job) stops holding an SDL_Surface
    pointer. It holds a simple struct with pixels/width/height instead.
  - CDevice creates an IWindow instead of an SDL_Window, and gets the
    IFrameBuffer from it.
  - CBaseGame uses IWindow/IFrameBuffer for Flip/Clear/PollEvents instead
    of SDL calls.
  - CStatCounter sets window title through IWindow instead of SDL.
  - SDL is still initialized for audio, gamepad, and timer - just not for
    the window or rendering surface.

WHAT STAYS THE SAME
--------------------
  - All game logic, menus, state machines, scripting - unchanged.
  - SDL event types (SDL_Event) are still used throughout the codebase.
    The native window classes translate their events into SDL events via
    SDL_PushEvent so existing code doesn't need to change.
  - Audio (SDL_mixer), gamepads (SDL_GameController), timers - unchanged.
  - The triangle rasterizer (RenderTri) - unchanged, it just writes to
    a uint32_t pixel buffer regardless of where that buffer came from.
